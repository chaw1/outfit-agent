开发记录（卡点与过程）¶

从接到作业开始记，按时间顺序。每条写：做了什么 / 卡在哪 / 怎么解决 / 用时。

工作方式¶

这次按"AI 原生开发"的方式做：我负责定场景、定范围、拍板取舍和最终验收；Claude Code 负责把决策写成唯一契约（docs/设计.md）、拆成带验收标准的任务书（docs/codex/*_PROMPT.md）、亲自复测每一次交付并合并上线；Codex 按任务书在各自的 git worktree 里并行实现，只提交本地分支。任何交付都不信自报，以我和 Claude Code 的实测为准。

顺序上先调研实测、再设计、再搭工程底座、然后按设计还原主链路并在线上留证据，之后按 P1（产品完整度）→ P2（质量与体系）逐项"只增不改"地合入，最后做独立评审、全链路回归与录屏。各期范围见 docs/设计.md §1.1。

12:40–12:50 真机第一次真实上传失败：换原生上传通道¶

  • 真机从相册选图后立刻报"图片没传好"，服务器和 nginx 都没有收到请求，说明请求没出手机。排查：React Native 的 FormData 文件描述符（{uri, name, type}）在真机上对相册文件不稳定；Web 端用 File 对象没有这个问题，所以假服务端到端和 Web 线上回归都测不出来。
  • 修法：原生端改用 expo-file-system/legacy 的 uploadAsync（iOS 走 NSURLSession、Android 走 OkHttp，直接按文件 URI 做 multipart），Web 与 Node 测试保持 fetch + FormData；按平台文件后缀分开（upload.ts / upload.native.ts），客户端只依赖一个注入点。重新装机后由本人在真机验证。
  • 顺带发现服务端有全局模型花费上限（MODEL_BUDGET_CNY，线上原设 60 元），最终录像时一键出片被它拦下交回用户。这是演示前必须拿掉的护栏：演示期间把上限提到实际不可能触及的数值，由账户余额兜底。

12:50–13:10 真机体验收口：图片分级预览、查看器、差异点文案¶

13:15–13:50 真机卡顿的根因是服务器出口带宽，媒体链路按"弱网"重做¶

  • 量化：从服务器拉文件实测只有约 3.5 Mbps（450 KB/s 左右）。一张 1536×2048 的成片 PNG 约 6 MB，要 13 秒；一条 5 秒 720P 视频 6–8 MB，要 15 秒以上。这就是真机上"图一直转圈、视频点播放黑屏"的全部原因：不是渲染问题，是带宽。笔记预览的轮播图之前也在拉原图。
  • 媒体链路改成默认弱网可用：
  • 成片在生成时就预先生成 360 / 720 / 1080 三档 JPEG 预览（原 PNG 带 AIGC 元数据，保留给保存到相册与导出用）；删除项目时预览与原图一起清理。
  • 视频在落盘前用 ffmpeg 重新编码（H.264、恒定质量 27、峰值码率 1.8 Mbps、faststart），5 秒短片从 6–8 MB 压到约 1 MB，失败则保留原片；服务镜像加入 ffmpeg。
  • App 的笔记轮播改走 720 预览；视频点播放后海报不再立刻消失，改为海报 + 转圈，直到播放器真正可播才切换，避免黑屏。
  • 笔记预览页按小红书的阅读结构重排：作者行在最上面，图片轮播限制在屏幕上半（保持 3:4），标题与正文不用下滑就能看到，调整图片顺序与草稿操作放到正文之后。
  • 带宽本身：演示期间把 ECS 公网带宽临时提到 100 Mbps（按流量计费），演示后恢复。这件事说明一个产品判断：穿搭类产品的核心成本不只在模型调用，媒体分发（对象存储 + CDN、预览分级、视频转码）要从第一天进入架构，而不是把原图直接从应用服务器吐给手机。
