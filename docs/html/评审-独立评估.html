衣序 outfit-agent 独立评估¶

评审日期：2026-10-21（Asia/Shanghai）。源码基线：3d7577de4a11b0283651ee743837852b285c729e。评审从 07:46:53 开始，限时 40 分钟。本文件是唯一新增产物；未改代码、未提交、未读取凭证或 private 目录，线上仅执行一次 GET /api/health。

1. 一句话总评与下一轮建议¶

有保留推荐进入下一轮：这份作业已经证明候选人能把真实模型、持久化工作流和移动界面接成完整通路，但“任务成功”与“内容可交付”仍然脱节，重试、改图采纳和草稿同步中的断点，尚不足以支持让他直接独立负责生产内容链路。

六项等权均分约 7.3/10。下一轮应重点考察候选人能否亲自解释并修复下述跨端问题，而不是继续展示新增了多少功能。最有说服力的补交，是“失败版本不再默认入稿、明确重试真的产生一次新尝试、改完能采用、最新文案能发布”这一小轮闭环。

当前证据证明了真实服务上的 Web 手机视口流程；原生 App 从登录到导出发布的真机闭环、正式平台发布结果、生产故障恢复演练，均未验证。不能据此判定这些功能一定坏了，也不能将其算作已验收。

3. Top 10 问题（按影响 × 可修性排序）¶

影响、可修性各按 1–5 评分，数值越高分别代表影响越大、越容易在当前交付周期处理；同分优先排用户会直接遇到的内容或操作问题。耗时是建议实施和定点验证的估计，不代表本次已修复；相邻问题可共享改动，不能机械相加。

1. 已知质检失败的版本会默认入稿，改图意图还可能被写成文案事实（5 × 5 = 25）¶

  • 现象： 袖口没放平，任务仍是 succeeded，App 默认选最高版本；服务端接受入笔记和视频。更危险的是，写笔记的提示词将“用户要求怎么改”当作比旧画面描述更高优先级的事实。这里的 succeeded 适合表示拿到了媒体，不能直接代表满足品牌要求。
  • 证据： run-1/evidence.json:388 的 editCheck.passed=false；:398–410、:683–686 显示失败新版进入选图和笔记。app/src/components/Cards.tsx:131–139 的默认选择只检查版本、status 和 URL；server/app/workflow.py:78–90、:273–289 没有质量确认门；worker.py:834–841 保存检查结果后仍标 succeeded；providers.py:187–190 明确要求正文服从改图 instruction。实际文案是否在每次都产生错误，未验证。
  • 面试官会追问： “系统已经知道没改成功，为什么默认把它送去发布？图没塞腰，文案却写塞腰，谁为品牌负责？”
  • 建议改法： 保留失败版供对比，但默认沿用上一版；用户主动采用未通过/未核对版本时明确确认。服务端同步验证该确认，视频源图也遵循同一规则。文案上下文分开 requested_change 与可确认画面事实，失败指令不得直接转为事实；还原分、人像分和指令核对分开表达。不要简单把所有质检失败都改成任务 failed，避免误触发付费重试。
  • 预计耗时： 60–90 分钟，含失败版默认选择、人工采纳和文案上下文的定点测试。语义修改成功率的提升不在这个时间承诺内。

2. 查看器“再试一次”与服务端内容去重冲突（5 × 4 = 20）¶

  • 现象： 用户看见“可能没改到位”后点“再试一次”，App 重发原编辑动作，服务端直接返回旧任务，实际没有新一轮生成；查看器却在等新 ID，存在持续等待的路径。
  • 证据： app/src/components/ImageViewer.tsx:337–341 原样构造 retryAction，:324 把已有 ID 记入 knownIds，:422 将按钮接到 sendEdit；server/app/workflow.py:730–738 以父图、指令和选区做稳定去重，并无条件返回 existing。跨端静态确认，本次未动态点击复现。
  • 面试官会追问： “网络重放和用户明确购买一次新尝试，为什么用了同一种幂等语义？”
  • 建议改法： 给“明确新尝试”独立 attempt/request ID，传输重放复用同一个 ID，用户再次确认才创建新 ID；后端保留旧尝试与版本链，校验预算和次数。更新 schemas、App Action 类型与设计约定。短期若不能完成契约，就撤掉误导按钮，明确指引改说法或重新选区；不能靠悄悄给指令加空格绕过去重。
  • 预计耗时： 60–90 分钟，含“同请求不多花、明确新尝试产生一个新任务”的验证。

3. 笔记阶段能改图，却不能顺手把新版采用到成稿（5 × 4 = 20）¶

  • 现象： 笔记写完后仍能进入查看器改图，但工作台只显示笔记卡，预览只按旧 image_ids 展示；自由文本说“用新版”也不会替换选图。用户花了改图费用，最终稿可能继续用旧图。
  • 证据： app/src/app/projects/[id].tsx:108、:113 分别隐藏 images 卡并允许 note 阶段编辑；preview/[id].tsx:124 只取 note.image_ids；server/app/workflow.py:787 保留笔记与阶段，:511–519 在 note/video/done 的文字修订路径强制保留原选图。后端 note 阶段已支持 approve_images（:223、:229、:238），因此不是必须重写服务端能力。
  • 面试官会追问： “博主看中新版本之后，在哪里按一下让它成为最终第二张图？”
  • 建议改法： note 阶段增加“重新选图”或“采用此版本”，保留原顺序并替换对应镜头，复用 approve_images；显式刷新笔记和发布草稿。video/done 维持当前定稿规则，别临时打开重新生成视频的复杂状态。
  • 预计耗时： 45–60 分钟，含“生成笔记→改图→采用→预览与导出一致”的验证。

4. 本地草稿会盖住后续服务端修订，缺少冲突选择（4 × 5 = 20）¶

  • 现象： 保存过本地草稿，再回聊天修改标题、正文或选图，打开预览仍可能看到旧稿；页面内存已有 draft 时，甚至无需保存就会继续盖住新的服务端 note。用户难以判断到底哪个版本会被复制发布。
  • 证据： app/src/app/preview/[id].tsx:97 仅在 current 为空时初始化草稿，:120 始终 applyNoteDraft；app/src/lib/noteDraft.ts:27–28 无条件覆盖正文、标签和图片 ID，:67 的持久化记录没有源 note 指纹/修订号，也没有恢复服务端稿入口。
  • 面试官会追问： “本地手改和 Agent 新生成发生冲突时，用户如何知道并决定？”
  • 建议改法： 存源笔记指纹与 dirty 状态；未编辑自动跟随服务端更新，已编辑则提示保留本地/采用新版，增加“恢复服务端版本”；旧草稿保留，不通过直接清空本地数据解决。将选图变更一并纳入冲突检查。
  • 预计耗时： 35–60 分钟，含重新聚焦、刷新恢复与源笔记更新的验证。

5. 终态生成失败后，普通用户缺少可用的恢复路径（5 × 3 = 15）¶

  • 现象： 图片失败提示“在对话里告诉我”，但重发同动作会复用失败任务；视频失败仍停在 video，已有重试卡的显示条件主要面向 note/confirm_video，可能根本不出现。管理员可以处理，博主不能自助继续。
  • 证据： app/src/components/Cards.tsx:182、:262–275；server/app/main.py:454–457 只将成功视频投影为 done；worker.py:881 将失败落库；workflow.py:563–566、:848–858 复用任务；可用的显式 retry 接口在 admin.py:385，且 :390–391 正确拒绝未知计费结果。
  • 面试官会追问： “供应商失败后，这一单是联系管理员，还是用户自己能继续？哪些失败绝不能自动重发？”
  • 建议改法： 区分已知可重试失败、仍在上游运行、结果/计费未知。后续提供带归属校验、限次与预算检查的用户重试契约；本轮至少让失败状态、下一步和管理员处理入口说明准确。复用已有保护，不把管理员的 reset 直接无条件暴露给用户。此问题与问题 2 共用部分恢复逻辑，但一个是终态失败，一个是媒体已返回而质量不达标。
  • 预计耗时： 完整自助恢复 60–90 分钟；只补准确状态与可执行指引 15–20 分钟。本次未注入供应商失败实测。

6. “App 交付”仍缺从登录到发布准备的原生真机验收（5 × 3 = 15）¶

  • 现象： 最强的完整链路证据来自 390×844 无头 Web；模拟器已有原生编译和启动记录，但只到引导/登录。相册权限、视频保存、双指手势、键盘遮挡、后台通知与冷启动跳转还没有同等强度证据。
  • 证据： app/LIVE.md:2 明确未做 iPhone 实机；docs/开发记录.md:75–80 明确原生后续未验；app/src/lib/media.ts:28、:38、:50 是真实原生 API 分支。第六轮 e2e/round6.spec.ts:271 构造表单状态，:276 替换 navigator.share，不能证明 iOS 分享成功。
  • 面试官会追问： “给我手机安装包；拒绝照片权限后再允许，能保存这组三图和视频吗？”
  • 建议改法： 若已有可用个人开发包，用一台实际手机验证登录、选图上传、放大圈选、权限拒绝/恢复、顺序保存与视频播放；优先复用现成项目，避免为了验交互重复付费。记录机型、系统、构建和未通过项。后台通知的及时性也未验证，现有实现依赖后台任务调度，不能承诺任务完成即刻通知（notificationRuntime.native.ts:120）。无法及时拿到可用包就明确以 Web 演示交付。
  • 预计耗时： 已能安装时 45–90 分钟；若签名、构建或设备条件不具备，耗时未验证，必须设停止点。缺证据不是已证实原生故障。

7. 普通 REST 没有明确超时，弱网恢复口径不完整（3 × 5 = 15）¶

  • 现象： 登录、上传、建项目和状态读取没有应用层 deadline；连接迟迟不结束时页面可能长时间忙碌。若建项目已落库却超时，简单让用户重按还可能造成重复项目。
  • 证据： app/src/api/client.ts:86–107 的 fetch 与 response.text 均无超时控制；同文件 :216 的 SSE 则明确设置 120 秒。新建页逐张上传后等待建项目，操作期间禁用主入口（app/src/app/projects/new.tsx:42、:50、:110）。缺少超时控制为代码事实；具体弱网等待时长未验证。
  • 面试官会追问： “地铁里请求挂住怎么办？超时表示没写入，还是只表示没收到回包？”
  • 建议改法： REST 加分类超时和取消，对读取允许显式重试，对创建结果不明先核对项目；不自动重放写请求。上传提示当前第几张、保留已上传项。下载媒体的 fetch 也应采用同类期限，但不在今天扩成通用网络框架。
  • 预计耗时： 30–45 分钟，含超时、收包中断和结果不明的定点测试。

8. 最终验收批次、费用和演示证据没有统一入口（3 × 5 = 15）¶

  • 现象： 同一个 run-1 名字已经对应新一轮证据，旧文档仍介绍旧联调；读者难以判定“最终通过”是哪次、哪版、覆盖哪些能力。备用回放也不是当前这次从注册开始的连续录制。
  • 证据： README.md:19 指向 app/LIVE.md 的 run-3；LIVE.md:1、:24 仍写 run-1 失败；docs/交接.md:12 写 02:33、117 秒、约 4.2 元。当前 run-1/evidence.json:5–6 实际为上海 07:41:20–07:46:23，编辑约 77 秒；observations.noteCostCny=4.164533 是视频前快照，latestState.cost_cny=5.68522 才是该记录的最终项目估价。walkthrough/线上项目回放.mp4 长 76.84 秒、无音轨，抽样中 20 秒已到完成项目、55–60 秒仍出现加载/黑屏，属于另一项目的界面回看。
  • 面试官会追问： “你说的 4.2 元包含视频吗？这段视频能证明今天这版 App 从注册到交付吗？”
  • 建议改法： README 放唯一最终验收索引：commit、当地时间、不可覆盖的 run 标识、项目、真实/Mock、Web/原生、费用时点、通过与失败项。旧报告显式标历史，不抹掉失败记录。演示脚本区分卡片先到和预览约一分钟后齐备，解释局部改失败；重录短讲解或明确标“已完成项目回放”。
  • 预计耗时： 文档 20–30 分钟，重录 30–45 分钟。当前线上部署与本地 commit 完全一致，未验证；health 的 0.1.0 不能代替部署 SHA。

9. 自动预览允许收费，但“换一组”缺少即时费用提示（3 × 5 = 15）¶

  • 现象： “换一组”看起来像普通对话操作，实际会再生成 2–3 张付费预览。首次引导正文承认自动收费，标题却说“花钱前，由你来确认”；用户容易将正式出图的确认承诺理解为覆盖所有生成。
  • 证据： app/src/components/Cards.tsx:315 没有报价；Onboarding.tsx:11 的标题与正文；server/app/workflow.py:378–388、:633–656 生成新方向及预览，views.py:29–40 只给脚本确认和视频确认估价。仓库当前估价下每组预览图片约 1–1.5 元，文本/视觉另计，实际账单未验证。
  • 面试官会追问： “用户连续换五组，钱从哪里扣？为什么没看到这次的价格？”
  • 建议改法： 在方向区和“换一组”旁显示“包含 2–3 张预览，会产生费用”，优先从服务端返回本轮估价，避免 App 再硬编码单价；引导标题改为准确的“正式出图和视频由你确认”。自动预览本身符合现有设计，不需要为此推翻流程或新做充值系统。
  • 预计耗时： 文案与提示 20–30 分钟；若增加统一报价字段，约 30–45 分钟。

10. 作业必交的“开发感受”仍只有提纲（4 × 3 = 12）¶

  • 现象： 工程功能不断追加，但题目要求的个人总结尚未成稿。面试官会把它理解为没有完成交付检查，也更难判断候选人本人理解了哪些取舍。
  • 证据： docs/交接.md:7 将开发感受列为必交；docs/开发感受.md:3 写“由 Gary 本人写”，:5–22 仍是提纲与素材。
  • 面试官会追问： “这些方案和修复里，你本人做了什么决定？哪次绿灯验收其实验错了？”
  • 建议改法： 由本人补 600–1000 字，讲一次拆题、一处判断失误、一项复测证据与一项未解决限制；将第一版关键词路由、App 未真联调、袖口失败三个事实择一讲透。不要代写亲身感受，不要继续增加流水账。
  • 预计耗时： 本人 20–30 分钟，再留 5–10 分钟检查与最终证据是否一致。

5. 面试追问清单¶

# 面试官最可能问的问题 一句话应答要点（基于当前仓库事实）
1 七个阶段手写也能做，为什么用 LangGraph？ 当前真实用了 PostgresSaver、interrupt/resume、中间卡片流和 checkpoint 脚本历史，代价是要维护图与业务投影的恢复，单纯七阶段手写也可行（graph.py:105、:152、:195；main.py:380）。
2 这真是 ReAct 吗，哪里有自主性？ 自由文本由模型从阶段白名单选一个工具并填参数，代码管归属、阶段和付费确认；它是受约束的单轮工具选择，并非通用多步自主循环（providers.py:155、:696；workflow.py:23）。
3 重复确认、断网与用户点“再试一次”有什么区别？ 稳定任务 ID 和去重键能防重复入队，但当前质量重试复用同动作会被去重，这是必须补的语义缺口，不能用 E2 通过掩盖（workflow.py:555、:730；ImageViewer.tsx:337）。
4 Worker 重启或被抢租约，如何避免旧结果覆盖？ 队列有 SKIP LOCKED、租约心跳和 attempts fencing，视频保存上游 task ID 后可继续查询；未知同步请求不会盲重发，不能宣称外部供应商调用实现了严格 exactly-once（worker.py:116、:738；providers.py:1252）。
5 还原 95 分能代表可发布、衣服正确吗？ 这是看图模型的估计，与人像一致、指令达成不同；当前袖口失败仍获高分并入稿，必须把质检、人工采纳与文案事实连接起来（run-1/evidence.json:388、:647；providers.py:187）。
6 圈外不变，是原生 inpainting 能力吗？ 服务端用裁剪生成加蒙版内贴回和羽化保证边界，已有像素测试；这只能证明边界保持，不能保证“袖口放平”这样的语义修改成功（local_edit.py；tests/test_local_edit.py；docs/设计.md:203）。
7 图、checkpoint 和消息三份状态，哪个是真相？ checkpoint 管对话决策与脚本，jobs 管生成结果，业务消息和项目阶段是展示投影，读接口在拿得到项目锁时尝试修复缺失任务/消息（main.py:380；workflow.py:586；server/README.md:55）。
8 为什么最终成本不是 4.2 元，失败会自动退款吗？ 4.164533 元是当前证据的视频前快照，最终估价为 5.68522 元；账本是估算和预留，不是充值扣点系统，也没有证明供应商失败必退款（run-1/evidence.json 的 noteCostCny/latestState.cost_cny；runtime_settings.py:135）。
9 发布闭环和原生 App 到底验证到哪里？ 已证明真实后端的 Web 全流程和 mock 草稿/分享调用，当前实际实现是复制文案、保存媒体后分享文字，原生相册/通知/手势和平台发帖仍未验证（media.ts:86；round6.spec.ts:276；docs/开发记录.md:79）。
10 如果接入更多真实品牌，下一周先做什么？ 先补质量确认、正确重试、成稿版本同步和失败恢复，再用多衣服/多人像的固定评测集检验质量；现有素材主要自生成，短对话和高分样例不能证明规模化稳定性（fixtures/README.md；workflow.py:159；本报告问题 1–7）。
