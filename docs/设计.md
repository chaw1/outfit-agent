# 穿搭笔记智能体（outfit-agent）设计

> 本文是后端和 App 共同遵守的唯一约定。接口有变化先改这里。

## 1. 场景

用户是小红书穿搭博主。品牌方（金主）发来一条合作需求，往往只有几张衣服图和一两句话。博主打开 App，新建一个合作项目，和智能体多轮对话：

1. 智能体先看懂衣服（品类、颜色、面料、风格），复述品牌需求。
2. 智能体主动给出 2–3 个**场景 + 风格方向**（AI 建议），博主挑一个，或者说"再松弛一点""换成通勤"继续聊。
3. 方向定了，智能体写出**笔记脚本**：标题备选、封面怎么拍、每张图的场景/穿搭/动作/配文、视频分镜。博主可以在对话里改，确认后才开始花钱生成。
4. 按脚本**批量出图**：博主本人照片（没有就用 AI 模特）× 品牌衣服 × 场景。
5. 博主挑图，不满意的在对话里说"这张衬衫塞进裤腰""背景太暗"，智能体**改图**，保留版本。
6. 产出最终**图文笔记**：标题、正文、话题标签、图片顺序。
7. 可选：用选中的图生成 5 秒**短视频**。

这是公司线上"品牌需求 → 博主内容"链路的 mini 版：只做一个博主、一个项目内的完整闭环。

### 1.1 产品范围与分期

24 小时只够把一条链路做扎实，但设计时按完整产品来规划，分三期落地，每一期的契约都在本文对应的节里：

| 期 | 范围 | 约定所在 |
|---|---|---|
| **P0 主链路** | 看懂衣服 → 场景 / 风格方向 → 脚本 → 批量出图 → 局部改图留版本 → 图文笔记 → 5 秒视频；人在回路（花钱前确认）；生成走队列 | §2–§6、§8 |
| **P1 产品完整度** | 两种创作模式（一键出片 / 沉浸编导）与风格词条；点数而非货币；账号闭环（协议与隐私、恢复码找回、修改密码、注销）；博主档案与项目管理；过程透明、花钱前预估、换一组；参考图与封面锚点；发布闭环；离开再回来的进度与通知；素材库（模特、衣服、成片沉淀为本人可复用的数据）；管理端 | §7、§9–§12、§14、§15、§18 |
| **P2 质量与体系** | 改图结果可信闭环（质检失败不默认入稿）；摄影感出片；设计系统（token 单一来源、组件库、组件实验室、视觉回归）；工程规范（CI 门禁、钩子、覆盖率、ADR） | §13、§14.3、§16、§17 |

UI 以 `docs/UI设计稿.md`（信息架构、流程、视觉语言、页面高保真稿与状态、组件规格；设计板 `docs/design/index.html`）为上游依据，本文只定数据与接口契约。

实施顺序：P0 先在线上跑通并留证据，再按 P1 → P2 逐项合入，每项"只增不改"，老客户端不受影响。

## 2. 架构

```
iOS / Android App（Expo + React Native + TypeScript）
        │ HTTPS：REST + SSE（对话流式输出）
        ▼
API 服务（FastAPI）──── 智能体（LangGraph，PostgresSaver 持久化，thread_id = 项目 id）
        │                    │ 工具调用
        │                    ├─ 文本：DeepSeek（deepseek-flash，function calling）
        │                    ├─ 看图：通义 qwen3-vl-plus
        │                    └─ 生成任务入队（不在对话里同步等）
        ▼
PostgreSQL ── 业务表 + 任务队列表 + LangGraph checkpoint 表
        ▲
Worker（独立进程，SELECT … FOR UPDATE SKIP LOCKED 取任务）
        ├─ 试衣/换景/改图：豆包 Seedream 5.0 pro（多图参考，实测 42 秒/张；备选 wan2.7-image-pro 14 秒/张，管理端可切）
        └─ 图生视频：wan2.6-i2v-flash（720P 5 秒，实测 52 秒）
媒体文件：服务器本地卷 /data/media（模型返回的 URL 只有 24 小时，必须下载转存）
部署：docker compose（api、worker、postgres、caddy 自动 HTTPS）
```

为什么生成走 Worker：一张图 15–45 秒、一条视频约 1 分钟，同步等会让对话卡死，也扛不住 App 断网重连。对话只负责"决定生成什么"，Worker 负责"生成出来"，结果写回项目状态，App 轮询或下一轮对话里看到。

## 3. 智能体

### 3.1 状态（LangGraph State，按项目持久化）

| 字段 | 说明 |
|---|---|
| `stage` | `brief` → `direction` → `script` → `images` → `note` → `video` → `done` |
| `brief` | 品牌需求原文 + 智能体整理后的要点 |
| `garments` | 衣服资产 id 列表 + 看图结果（品类/颜色/面料/风格标签） |
| `model_asset_id` | 博主本人照片；为空则用默认 AI 模特 |
| `directions` | 智能体给出的方向列表；`chosen_direction_id` |
| `script` | 结构化脚本（见 4.4 `script` 卡片），`status: draft / confirmed` |
| `images` | 每个镜头的图片版本链（`shot_id`、`version`、`parent_id`） |
| `note` | 标题、正文、标签、图片顺序 |
| `video` | 视频任务和结果 |
| `messages` | 对话历史（LangGraph `add_messages`） |

### 3.2 人在回路（花钱前必须博主确认）

- 选方向：智能体给出方向后停下，等博主选或继续聊。
- 确认脚本：脚本确认后才允许出图。
- 确认出视频：视频最贵，单独确认。

用 LangGraph `interrupt()` 停下，App 发来的动作（`action`）通过 `Command(resume=…)` 恢复。博主随时可以发自由文本，智能体在当前阶段内回答或修改。

### 3.3 工具（智能体可调用）

`analyze_garments`、`propose_directions`、`write_script`、`revise_script`、`generate_images`（入队）、`edit_image`（入队）、`write_note`、`generate_video`（入队）。工具按阶段放行：脚本没确认不能出图，没有图不能写笔记、出视频。

## 4. 接口约定

所有接口前缀 `/api`，JSON，`Authorization: Bearer <token>`（注册/登录除外）。时间用 ISO 8601。错误统一 `{"error": {"code": "...", "message": "中文说明"}}`。

### 4.1 账号

- `POST /api/auth/register` `{username, password, nickname?}` → `{token, user}`
- `POST /api/auth/login` `{username, password}` → `{token, user}`
- `GET /api/me` → `user`
- `user = {id, username, nickname, created_at}`；用户名 3–32 位，密码至少 8 位，bcrypt 存储，JWT 7 天。

### 4.2 资产（图片/视频）

- `POST /api/assets`（multipart：`file`，`kind` = `garment | model | reference`）→ `asset`
- `asset = {id, kind, url, width, height, mime, created_at, source: "upload" | "generated", parent_id?, prompt?}`
- `url` 是带签名的绝对地址（`/media/{id}?exp=…&sig=…`，有效 24 小时），App 直接给 `<Image>` 用，不需要带 token。

### 4.3 合作项目

- `POST /api/projects` `{title, brand, brief, garment_asset_ids: [..], model_asset_id?}` → `project`
- `GET /api/projects` → `[project]`（按更新时间倒序）
- `GET /api/projects/{id}` → `project`
- `GET /api/projects/{id}/state` → `state`（App 渲染工作台用，见下）
- `DELETE /api/projects/{id}`
- `project = {id, title, brand, brief, stage, cover_url?, created_at, updated_at}`
- `state = {stage, garments: [garment], directions: [direction], chosen_direction_id?, script?, images: [image], note?, video?, active_jobs: [job], pending_action?}`
  - `pending_action`：智能体正在等的确认，`{type: "choose_direction" | "confirm_script" | "confirm_video", prompt}`，没有则为 null。

### 4.4 对话

- `GET /api/projects/{id}/messages` → `[message]`
- `POST /api/projects/{id}/messages` `{text?, action?}` → **SSE** 流（`text/event-stream`）
  - `action` 可选：
    - `{type: "choose_direction", direction_id}`
    - `{type: "confirm_script"}`
    - `{type: "edit_image", image_id, instruction}`
    - `{type: "approve_images", image_ids: [..]}`（选定用于笔记的图和顺序）
    - `{type: "confirm_video", image_id}`（`note` / `done` 阶段都可发；上一条短片做完或失败后再发就是新制作，状态里的 `video_attempt` 递增并进入去重键；上一条还在做时同图重发复用原任务，换图回 `video_in_progress`）
  - SSE 事件：
    - `event: token` `data: {"delta": "..."}` 智能体回复的文字增量
    - `event: card` `data: card` 结构化卡片（完整对象，同 id 后到的覆盖先到的）
    - `event: job` `data: job` 新建或更新的生成任务
    - `event: done` `data: {"message_id": "..."}` 本轮结束
    - `event: error` `data: {"code": "...", "message": "..."}`
- `message = {id, role: "user" | "assistant", text, cards: [card], action?, created_at}`

卡片（`card.type` 决定样式，`card.id` 稳定，可被后续事件覆盖更新）：

| type | 内容 |
|---|---|
| `garments` | `{items: [{asset_id, url, category, color, material, style_tags: []}]}` |
| `directions` | `{options: [{id, name, scene, mood, palette, why, sample_title, styling}]}`，`styling` 是整套搭配建议：博主只给一件单品时，配什么下装、鞋、配饰 |
| `script` | `{status, title_ideas: [], cover: {scene, pose, text_overlay}, shots: [{id, scene, outfit_asset_ids: [], pose, camera, caption, styling}], video: {prompt, duration}}`，每个镜头的 `styling` 是这一镜头的完整穿着（原衣服怎么穿 + 搭配的下装 / 鞋 / 配饰），在对话里改，确认脚本时定稿；出图提示词按它画，笔记正文写进它 |
| `images` | `{items: [image]}` |
| `note` | `{title, body, tags: [], image_ids: []}` |
| `video` | `{status, url?, poster_url?, job_id?}` |

`image = {id, shot_id, url?, status: "queued" | "running" | "succeeded" | "failed", version, parent_id?, instruction?, error?}`

### 4.5 生成任务

- `GET /api/jobs/{id}` → `job`
- `job = {id, project_id, kind: "image" | "edit" | "video", status: "queued" | "running" | "succeeded" | "failed", result_asset_id?, url?, error?, created_at, updated_at}`
- App 在 `state.active_jobs` 非空时每 3 秒拉一次 `/state`。

### 4.6 健康检查

- `GET /api/health` → `{ok: true, version, providers: {text, vision, image, video, mock}}`

| 用途 | 模型 | 实测 |
|---|---|---|

## 6. 数据表

`users`、`projects`、`assets`（含 `parent_id` 版本链、`prompt`、`model`、`source`）、`messages`（展示用，含 cards JSON）、`jobs`（队列：`status`、`attempts`、`locked_at`、`payload`、`result`）、`usage_ledger`（每次模型调用的模型名、耗时、计费单位）+ LangGraph 自带 checkpoint 表。迁移用 Alembic。

## 7. 智能体边界与合规（只增不改，旧字段语义不变）

### 7.1 智能体的边界

- **阶段之间是状态机**：哪个阶段允许哪些工具、花钱前必须确认，由代码决定，可审计。
- **阶段之内是 ReAct**：博主的自由文本交给模型，模型从当前阶段允许的工具里自己选（含只回复不动作的 `chat`），参数也由模型从上下文解析（比如"第二张""咖啡馆那张"对应哪个 `image_id`）。代码只校验和放行，不做关键词路由。
- **回复由模型写**：每个工具都带 `reply` 字段，模型用博主搭子的口吻顺手写一两句；模板句只作为模型失败时的兜底。

### 7.2 字段新增

- `direction` 增加 `preview_url?`、`preview_status?`（`queued | running | succeeded | failed`）：每个方向一张灵感预览图，出方向后自动生成（低成本层，约 0.5 元/张；批量出图仍要确认脚本）。
- `image` 增加：
  - `fidelity?: {score: 0-100, diffs: [string], auto_fixed: bool}`：生成后用看图模型对比原衣服打的"还原分"和差异点；差异点只作为自动修图的提示词，App 只展示分数徽章，不把模型口吻的差异描述暴露给用户；低于 60 分自动修一版（每张最多一次），新版本 `instruction` 写明修了什么。
  - `script_version?`：这张图是按第几版脚本生成的。
- `note` 增加 `cost_cny?`（这篇笔记累计花费估算）和 `ai_label`（AI 生成声明文案，App 在笔记预览里显示）。
- `state` 增加：
  - `cost_cny`：项目累计花费估算（元）；
  - `last_message_id`：最新一条消息的 id。后台任务完成时智能体会**主动发一条消息**（比如"4 张都好了，第 3 张口袋跑了我已经补了一版"），App 发现它变化就重新拉 `/messages`；
  - `script_versions: [{version, checkpoint_id, created_at, summary, current}]`：脚本历史，来自 LangGraph 的 checkpoint 历史。
- 新动作 `{type: "restore_script", checkpoint_id}`：把脚本恢复到某个历史版本，回到 `script` 阶段等确认，已有图片保留。

### 7.3 合规

生成的图片保存时带可见的"AI生成"角标和元数据标识；视频请求带水印参数。笔记预览提示博主发布时勾选平台的 AI 内容声明。

## 8. 手机上的图片交互与局部改

### 8.1 交互（App）

- **点图进全屏查看器**：左右滑切换图片，双指缩放、双击放大看细节（袖口、纽扣、面料）；底部是这个镜头的**版本条**（v1 / v2 / v3…，按 `parent_id` 链），可以拖动**前后对比滑块**看改了哪里。
- **局部改**：在查看器里进入"圈选"模式，用手指涂抹要改的地方（可调笔刷粗细、撤销、清空，也可切换成框选），再点快捷说法（袖口放下来 / 衬衫塞进裤腰 / 去掉吊牌 / 换颜色 / 背景亮一点…）或自己输入，提交后只改圈出来的区域。
- **整张改**：不圈选，直接说一句话改整张。
- **引用到对话**：长按图片或在查看器里点"引用"，输入框上方出现这张图的缩略图，博主可以说"这张袖口卷起来了"，智能体知道指的是哪张。
- **快捷话术**：沉浸编导下，输入框上方按阶段给两三句最常说的话（方向阶段"换一组方向"、笔记阶段"正文短一点，100 字以内"、做完短片后"再做一条短片"等），点一下直接发出；只放不花钱的自由对话，要花钱的确认仍走卡片按钮；生成进行中与一键出片模式不显示。
- **长按菜单**：局部改 / 整张改 / 引用到对话 / 对比版本 / 保存到相册。
- 改完的新版本自动出现在版本条里，并显示"是否按要求改好"的检查结果；没改到位可以一键重试或换个说法。

### 8.2 接口新增

- `edit_image` 动作增加可选字段（二选一，都不带就是整张改）：
  - `region: {x, y, w, h}`：框选，0–1 归一化，相对原图宽高；
  - `mask_strokes: {brush: 0–1（相对图片短边）, strokes: [[{x, y}, …], …]}`：涂抹轨迹，坐标 0–1 归一化。
- `POST /messages` 增加可选 `refs: [image_id]`（引用的图片）；`message` 增加 `refs`。
- `image` 增加：
  - `region?`：这一版是局部改时的区域（框选或涂抹外接框，0–1）；
  - `edit_check?: {passed: bool, reason: string}`：看图模型核对"指令有没有做到"。

### 8.3 服务端局部改的做法

按涂抹轨迹生成蒙版 → 取外接框并向外扩一圈上下文裁剪 → 只把裁剪块和指令（附原衣服图）交给生成模型，最后一张参考始终是唯一待编辑的裁剪画布 → 在蒙版内对齐边缘颜色和亮度，再按蒙版羽化贴回原图。**蒙版以外的像素保持不变**（测试验证）。上下文扩边按选区长边的 60% 取值（至少 16 像素）；指令描述需要看到的最终状态，保持未要求改变的品类与袖长，不把短袖展开误解为改成长袖；纯调色或亮度指令只改变对应属性。改完用看图模型核对指令是否做到，没做到自动加强指令重试一次，结果如实写进 `edit_check`。

### 8.4 吊牌与包装

衣服原图上的吊牌、价签、织标贴纸、衣架、包装袋不属于衣服：出图提示和还原分质检都要忽略它们，生成图里不能出现。

## 9. 管理端

### 9.1 定位

运营者视角的后台，和 App 共用同一个服务与数据库，不另起服务：页面在 `/admin`，接口在 `/api/admin/*`。独立口令登录（环境变量 `ADMIN_TOKEN`，只在服务器 `.env`），与 App 账号体系无关；App 用户拿不到管理接口。中文界面，手机浏览器也要能看（面试现场可能用手机打开）。

### 9.2 页面

| 页面 | 内容 |
|---|---|
| 总览 | 用户数、项目数、今日 / 累计模型调用次数与估算费用、项目按阶段分布、排队中 / 运行中 / 失败任务数 |
| 用量统计 | 按模型、按用户、按天（最近 30 天）的调用次数、耗时、估算费用；可按用户筛选；可导出 CSV |
| 模型与配额 | 四种能力（对话 / 看图 / 出图 / 视频）各用哪个模型（从候选列表选）；用户分层 `free` / `pro`，每层默认每日预算（元）和可用模型；全局每日预算；改了立即生效，不重启 |
| 任务队列 | 生成任务列表（状态、种类、项目、用户、尝试次数、错误原因、耗时）；失败任务一键重试；排队中的可取消 |
| 用户管理 | 列表（注册时间、项目数、累计花费、层级、状态）；禁用 / 启用；改层级 |

### 9.3 接口

- `POST /api/admin/login`：`{token}` → 会话（cookie 或 bearer，自选）；其余管理接口都要求已登录。
- `GET /api/admin/overview`

## 10. 博主档案、项目管理、发布闭环与工程成熟度

> 目的：面试官看到的不是"一个能跑的对话"，而是一条完整的产品通路——博主有自己的形象和偏好、项目能管理、笔记能一键发出去、后台有人能看能管、服务端有线上系统该有的防护。

### 10.1 博主档案（App「我的形象」+ 服务端）

- `GET /api/me` 增加：`tier`、`daily_budget_cny`、`today_cost_cny`、`profile: {model_asset_ids: [asset_id], height_cm?, body_notes?, style_notes?}`。
- `PATCH /api/me` `{nickname?, profile?}` → `user`。`model_asset_ids` 里的资产必须是本人上传的 `kind=model`。
- 新建项目时 `model_asset_id` 可不传：服务端取档案里第一张本人照片；`style_notes`（如"喜欢松弛感，不穿高跟鞋"）作为博主偏好进入智能体上下文，方向和脚本要照顾它。这是"博主风格记忆"的 mini 版。
- App 设置页加「我的形象」：管理本人照片（多张、设默认）、身高体型、风格偏好；新建项目时默认选档案照片，也可换。昵称可改。

### 10.2 项目管理（App）

- 项目列表：左滑或长按删除（二次确认，用现有 `DELETE /api/projects/{id}`）；按标题/品牌搜索；卡片显示阶段标签和封面；下拉刷新。
- 服务端删除项目时级联清理该项目的消息、任务、生成媒体文件（上传的衣服原图保留，可能被别的项目复用）。

### 10.3 发布闭环（App）

- 笔记预览页加「准备发布」：一步完成复制文案 + 保存全部图片（按顺序）+ 保存视频到相册，再弹系统分享面板；带一张"发布清单"（图片 n 张、视频、已勾选 AI 内容声明）。
- 生成完成本地通知：App 在后台时，批量出图 / 改图 / 视频完成弹本机通知（`state.last_message_id` 变化或任务完成触发），点通知进对应项目。

### 10.4 对话细节（App）

- 长按消息：复制文本；失败的用户消息可重发；智能体最后一条回复可「换个说法」（重新生成，只重跑本轮，不重复花钱——有付费动作的轮次不提供）。
- 首次打开三屏引导（能做什么、花钱前会确认、AI 声明）；关于页：版本、服务地址、隐私说明。

### 10.5 工程成熟度（服务端）

- 限流：注册 / 登录按 IP 每分钟上限，上传和对话按用户每分钟上限；超限返回 429 中文说明。
- 上传校验：只收 jpeg/png/webp/heic，单文件 ≤ 15 MB，最长边 ≤ 6000；超限 413/415 中文说明。
- 可观测：每个请求带 `X-Request-Id`（响应头回传），结构化 JSON 日志含请求 id、用户 id、项目 id、耗时；模型调用日志含模型名、耗时、费用。
- 配额：`today_cost_cny`、`daily_budget_cny` 与第 9 节管理端的层级一致。
- CI：GitHub Actions 工作流，服务端 ruff + pytest（Mock）、App typecheck + lint + 单测。
- 管理端（第 9 节）在总览加"最近 24 小时错误数"和请求量。

### 10.6 约束

- 全部只增不改：旧接口、旧字段语义不变；App 对不存在的新接口（404）要优雅降级（隐藏对应入口），保证旧服务端也能用。

## 13. 改图结果可信闭环

> 规划 P2「可信」：任务成功不等于内容可交付。改图没改到位的版本不能悄悄进入笔记和视频，文案不能把没改成的指令写成事实，"再试一次"必须是一次真正的新尝试。本节是服务端与 App 的唯一契约。


### 13.1 质检失败的版本不默认入稿

- 定义：一张图"未核对通过"= `image.edit_check` 存在且 `passed === false`。
- App 默认选择：每个镜头默认选**最新一张已成功且核对通过（或没有 edit_check）的版本**；未核对通过的新版本显示角标"未改到位"，不自动替换默认选择，也不自动进入选图顺序。
- 用户可以主动采用未通过的版本：查看器/选图处提供"仍然采用"，弹一次确认（显示 `edit_check.reason`），确认后 `approve_images` 带 `accept_unverified: [image_id]`。
- 服务端 `approve_images`：`image_ids` 里若含未核对通过的图而没有列在 `accept_unverified` 里，返回错误 `unverified_image`（消息列出镜头号和原因，App 用它弹确认后重发）；通过后 `state.note.accepted_unverified_ids: [image_id]` 持久化，App 在预览/发布清单里对这些图标"手动采用"。
- 视频源图走同一规则（源图必须在当前 `note.image_ids` 里，因此不需要新字段）。
- 写笔记上下文：把"用户要求怎么改"（requested_change）和"可确认的画面事实"分开传给文案模型；只有 `edit_check.passed === true` 或被用户主动采用的改图指令才能写成画面事实，否则按原衣服/原画面描述；提示词里明确"没有核对通过的修改不要写进文案"。
- 不把质检失败改成任务 `failed`（避免误触发付费重试）。

### 13.2 "再试一次"= 明确的新尝试

- `edit_image` 增加可选 `attempt: string`（客户端生成，≤ 64 字符，建议 `UUID`）。去重键 = 父图 + 指令 + 选区 + `attempt`。同一 `attempt` 重放 → 返回同一任务（网络重放不多花钱）；新的 `attempt` → 新任务（照常走预算与限流）。不带 `attempt` 时行为与现在一致。
- 服务端返回里标明本次是否复用：`pending_action` 或任务响应中 `reused: boolean`（放在现有改图回包的同级字段，App 以它判断要不要继续等新版本）。
- App：同一次用户提交只生成一个 `attempt`，传输层重试复用它；用户点"再试一次 / 换个说法"才生成新的 `attempt`；收到 `reused=true` 时不再无期限等新 ID，提示"这次和上次一样，没有重新生成"。

### 13.3 笔记阶段能采用新版

- 服务端已支持 note 阶段 `approve_images`（重新写笔记），不改语义，只保证：`approve_images` 在 note 阶段会重写 `note`，并保留用户已有标题/标签的改动不做要求（本地草稿由 13.4 处理）。
- App：note 阶段（`state.stage === 'note'`）在查看器版本条和笔记卡提供"采用此版本到笔记"/"重新选图"，用新版替换同镜头的旧版、保持顺序，发 `approve_images`；预览与发布清单随 `note.image_ids` 刷新。video/done 阶段维持定稿，不开放。

### 13.4 本地草稿与服务端修订的冲突（仅 App）

- 本地草稿记录来源指纹 `sourceFingerprint = sha256(title + body + tags + image_ids)` 和 `dirty`。
- 打开预览：`!dirty` → 直接跟随服务端最新笔记；`dirty` 且服务端指纹变化 → 顶部提示"笔记有新版本"，给"保留我的修改 / 采用新版本"两个按钮；任何时候都有"恢复服务端版本"入口。不清空用户草稿。

### 13.5 普通请求超时（仅 App）

- REST 分类超时：读取 20 s、写入 60 s、上传 120 s；用 `AbortController`，超时后读取类可重试，写入类**不自动重放**，创建项目超时后先刷新项目列表再决定是否重建。上传逐张显示"第 n/N 张"。SSE 保持现有 120 s。

### 13.6 "换一组"的费用提示

- 服务端 `directions` 卡片增加 `regenerate_estimate_cny`（按 `costs.py` 估算 2–3 张预览的费用）。
- App："换一组"按钮旁显示"约 ¥x · 含 2–3 张预览"；首次引导第二页标题改为"正式出图和视频，由你确认"。

### 13.7 约束

- 只增不改，没有新字段时行为与 §12 一致；线上回归用例 `e2e/live.spec.ts` 不需要改也应继续通过。

## 14. 两种创作模式、点数、摄影感出片与离开再回来

> 规划 P1 / P2：博主有两种状态——赶更新不想做选择题（一键出片），或想一步步打磨（沉浸编导）；对用户只展示点数不展示货币；出片要有摄影感而不是通用模型的"AI 感"；生成动辄一两分钟，离开再回来必须知道进度。本节是唯一契约，字段名照此。


### 14.1 点数（服务端 + App）

- 口径：**10 点 = 1 元**，`costs.py` 增加 `POINTS_PER_CNY = 10` 与 `points(cny) -> float`（保留 1 位小数）。出图 1 张 = 5 点，视频 = 15 点，换一组预览约 15 点，文本对话按实际折算（通常不到 1 点）。
- 服务端在所有现有 `*_cny` 字段旁增加同义的 `*_points` 字段，旧字段保留不改：`budget.{daily_budget_points, today_cost_points, remaining_points}`、`pending_action.estimated_cost_points`、`trace.cost_points`、`directions.regenerate_estimate_points`、卡片 `cost_points`、`GET /api/me` 的 `daily_budget_points / today_cost_points`。
- App 用户可见的任何地方只出现"点"，不再出现 ¥ / 元 / 费用 / 花费 / 价格：确认按钮旁"预计 15 点 · 今日还有 585 点"；消息下方"用了 写脚本 · 4.8s · 0.3 点"（不到 0.1 点显示"不到 0.1 点"）；点数不够时"今日点数不够了，明天 00:00 恢复"。设置页与引导页的措辞同步。
- 管理端仍按元统计（运营口径），页头注明"用户端以点数显示，10 点 = 1 元"。

### 14.2 一键出片（`mode: auto`）

- `POST /api/projects` 增加 `mode: "guided" | "auto"`（默认 `guided`，老客户端不变）和 `style_tags: list[str]`（≤ 6 条，每条 ≤ 12 字；进提方向与写脚本的上下文，不改 brief 原文）；`projects.mode`、`projects.style_tags` 新列（迁移 0010）；`ProjectOutput` 与 `state` 回 `mode` 与 `style_tags`。
- `GET /api/quotes/auto` → `{estimate_points, breakdown: [{label, points}]}`：预览 3 张 + 正式出图 3 张（含自动修一版 20%）+ 视频 1 条，按 `costs.py` 估算（当前约 48 点）。App 在"开拍"按钮上显示它。
- auto 行为（服务端）：三个人在回路点自动走默认——方向取 `propose_directions` 标记的 `recommended: true` 那个（模型按 style_tags 与 brief 推荐，缺省第 1 个）；脚本写完立即确认并入队出图；出图完成后自动采用全部 v1（封面 = 封面锚点，跳过核对失败的版本）→ 写笔记 → 自动确认视频 → 视频完成 → `done`。任何一步失败（任务 failed、点数不够、模型错误）停在当前阶段，`mode` 转回 `guided`，发一条主动消息说明停在哪、为什么、下一步怎么做。
- `state.auto: {active: bool, step: "directions"|"script"|"images"|"note"|"video"|"done", label: string, started_at, estimate_points}`；auto 进行中 `pending_action` 始终为 `null`，每步切换发一条主动消息（和出图完成的主动消息同一通道）。
- `POST /api/projects/{id}/mode {mode: "guided"}`：从下一个人在回路点起停下等用户，已在跑的任务不取消；回 `state`。auto 中用户仍可发消息，`chat` 正常；`ALLOWED_TOOLS` 不变。

### 14.3 摄影感出片（服务端）

### 15.2 同意与首次启动

### 15.3 忘记密码（恢复码）

- 注册成功响应增加 `recovery_code`（12 位，`xxxx-xxxx-xxxx`，只在这一次返回，服务端只存 hash）。App 用整页展示：这是唯一的找回方式，提供"复制"，用户点"我已保存"才进入。
- `POST /api/auth/recover {username, recovery_code, new_password}` → 验证通过则重置密码、作废旧登录、换发新恢复码并返回 `{token, user, recovery_code}`；失败统一回 `RECOVERY_FAILED`，按用户名限流（现有 `rate_limits`）。
- `POST /api/me/recovery-code {password}` → 重新生成并返回新恢复码（设置页"重新生成恢复码"）。
- 登录页"忘记密码？"→ `/forgot`：用户名 + 恢复码 + 新密码；成功后展示新恢复码并登录。

### 15.4 修改密码与登录失效

- `POST /api/me/password {current_password, new_password}` → 修改并作废此前签发的所有 token（`users.password_updated_at`，早于它签发的 token 一律 401），当前设备拿到新 token。
- 以上三处（改密码、换恢复码、注销）的当前密码校验失败回 400 `INVALID_PASSWORD`，登录态不变；401 只表示会话失效，客户端收到 401 才退出登录。

### 15.5 注销账号

## 18. 素材库：模特、衣服与成片沉淀为本人数据

> 规划 P1：博主每拍一组片，产生的模特形象、上传过的衣服、挑中的成片都应沉淀为本人的素材，下一组片可以直接复用——尤其是"同一个模特"：固定出镜的人是小红书账号人设的一部分。底子已经有：生成时第一张参考图就是 `model_asset_id`，提示词要求保持参考图中的模特身份（§6）；档案里的 `model_asset_ids` 已可作为出镜的人（§10.1）。本节只补"把成片里的人存下来"和"把本人素材集中管理"两件事，不新造概念。

### 18.1 服务端

- `POST /api/me/models/from-image` `{image_id, name?}` → `{asset, user}`。把某张本人项目的成片存为模特素材：复制该成片文件为新资产 `kind=model, source=generated, parent_id=成片资产 id, project_id=来源项目`，并追加到 `profile.model_asset_ids`（沿用 20 张上限，超限 422 中文说明）。同一 `image_id` 重复存返回同一资产（幂等）。`name` 存在 `asset.analysis.name`（如"操场那组的她"），缺省取来源项目标题。
- `GET /api/me/assets?kind=model|garment|image&limit=&offset=` → `{items: [AssetOutput + {project_id, project_title, created_at, source, name?, in_profile: bool}], total}`，只含本人资产，按时间倒序。`kind=image` 指各项目 `status=succeeded` 的成片（含改图版本）。
- `DELETE /api/me/assets/{id}`：模特素材从 `profile.model_asset_ids` 移除并删除文件（`source=generated` 的副本；正被未删除项目选作出镜人时 409 `ASSET_IN_USE` 并列出项目，和衣服一致）；上传的模特只从档案和素材库列表中移除（`analysis.library_hidden`），文件与项目引用保留；上传的衣服仅在没有项目引用时删除，否则 409 说明被哪些项目使用；成片不在此删除（跟随项目，§10.2）。
- 衣服复用：`POST /api/projects` 的 `garment_asset_ids` 可引用本人任何 `kind=garment` 资产，不限制必须是本次上传（现有校验已满足，补测试固定这一行为）。
- 注销（§15）清理本人全部资产时一并覆盖本节新增的副本。
- 迁移：不加表；`in_profile` 与 `name` 由现有字段推导，`0012` 仅在需要索引时新增。

### 18.2 App

- 图片查看器与挑图页的动作区加「存为我的模特」：成功后角标「已在我的模特」，再次点击不重复存（幂等）。旧服务端 404 → 隐藏该动作。
