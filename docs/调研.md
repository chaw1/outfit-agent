# 场景调研与技术选型

> 作业：24 小时交付一个"小红书博主 × 品牌合作"内容智能体的 App demo。本文先讲清楚场景，再讲生成能力和智能体框架为什么这么选。实测数据全部来自 2026-10-20 当晚的真实调用，素材在 `docs/spike/`。

## 1. 场景：一篇品牌合作笔记是怎么做出来的

### 1.1 角色

| 角色 | 想要什么 |
|---|---|
| 品牌方（金主） | 新品尽快被种草；图里的衣服必须和实物一致；内容调性符合品牌 |
| 博主 | 少花时间、少花钱接更多单；内容保持自己的风格，不像硬广 |
| 平台（小红书蒲公英） | 品牌找博主、下单、报备笔记的官方通道；对广告和 AI 内容有规范 |

### 1.2 今天的流程和卡点

```
品牌发 brief（几张衣服图 + 一两句卖点）
  → 博主想方案：场景、风格、怎么拍         ← 卡点①：只有几张图，靠博主自己脑补，来回沟通
  → 写脚本给品牌审                         ← 卡点②：脚本反复改
  → 等样衣、约场地/摄影/妆造、拍摄、修图    ← 卡点③：周期按天算，单套成本上百元
  → 写文案、排图                            ← 卡点④：标题、正文、标签都要贴平台语感
  → 品牌审稿，不满意重拍某张                ← 卡点⑤：改一张图 = 重拍一次
  → 发布报备笔记
```

参考数据：服装商拍团队自述，传统单套商拍 200 元以上、出图 5–7 天，用 AI 后单套 5–8 元、1 天内出图（[搜狐](https://m.sohu.com/a/998620694_122675809/)，团队自述数据，未独立核实）。另有评测指出 AI 模特图仍需人工确认光线、色调和服饰细节（同一组搜索结果，中文评测）。

### 1.3 智能体接手哪几段

| 原环节 | mini 链路里的一步 | 用到的能力 |
|---|---|---|
| 看懂品牌给的衣服 | 智能体看图，说出品类、颜色、面料、风格标签 | 多模态理解 |
| 博主想方案（卡点①） | 智能体主动给 2–3 个场景 + 风格方向，博主挑或继续聊 | 对话 + 审美建议 |
| 写脚本（卡点②） | 结构化脚本：标题备选、封面、每张图的场景/穿搭/动作/配文、视频分镜；对话里改 | 对话 + 结构化输出 |
| 拍摄修图（卡点③） | 按脚本批量出图：博主本人照片 × 品牌衣服 × 场景 | 多图参考生成（试衣 + 换景） |
| 改图（卡点⑤） | 说一句"衬衫塞进裤腰"，只重做那一张，保留版本 | 指令改图 |
| 写文案排图（卡点④） | 产出可直接发布的图文笔记 | 文本生成 |
| 加分项 | 选中的图生成 5 秒短视频 | 图生视频 |

博主还有两种工作状态，入口上要分开：赶更新、不想做选择题的时候要「一键出片」（交素材，直接拿全套）；想打磨的时候要「沉浸编导」（聊灵感、定脚本、挑图改图，每一步自己定）。两种模式走同一条链路，区别只是人在回路点是停下等人，还是按默认继续。

### 1.4 和 MuseGate 的关系

霖润的 MuseGate 已经覆盖出图、视频、设计、详情页、资产中心，其中 **Chiccify（即刻达人）** 面向创作者一键做小红书 / TikTok / Instagram 图文笔记；公开可见的"Agent 对话创作"流程是：上传服装和模特 → 出多组风格灵感图挑选 → 定主图 → 自动补全套配图和文案。

Chiccify 的功能清单、交互细节和与本作业的逐项对照见 [`docs/调研-Chiccify对照.md`](调研-Chiccify对照.md)（2026-10-21 凌晨补做：它是桌面 Web、没有 App；流程与本作业同构；它强在过程透明、预估扣点和发帖表单，本作业强在手机端全链路、对话内局部改、还原质检、脚本回滚、管理端）。

这份作业是这条链路的 mini 版：**只做一个博主、一个合作项目里从 brief 到成稿的闭环**。没做的部分（资产中心与自动打标、专属模特训练、详情页、多平台分发）在第 5 节列为演进方向。

### 1.5 必须守住的三条

1. **高还原**：衣服的颜色、面料、版型、logo 不能走样。这是品牌方付钱的前提（创始人原话："高还原是生死线，高审美是入场券"）。
2. **审美贴合博主**：场景和风格要像这个博主会发的内容，而不是千篇一律的棚拍。
3. **合规**：
   - 《人工智能生成合成内容标识办法》2025-09-01 起施行，要求生成的图片、视频、文本带**显式标识**（文字或图形提示），文件元数据带**隐式标识**，下载导出时也要保留（[新华网](https://www.news.cn/tech/20250319/a572ec4366f149c1b0b04a07ebf4931b/c.html)、[普华永道解读](https://www.pwccn.com/zh/tmt/method-identifying-synthetic-content-generated-ai-sep2025.pdf)）。笔记发布时还应使用平台的 AI 内容声明。
   - 肖像：模特只用博主本人上传的照片或 AI 生成的虚拟模特。
   - 品类：内衣、泳衣等敏感品类不做（MuseGate 也有同样限制）。

## 2. 生成能力选型（实测）

测试素材全部自己生成（避免肖像和版权问题）：用 qwen-image-3.0-pro 文生图生成一件米白亚麻衬衫、一条浅蓝直筒牛仔裤（平铺产品图）和一张站立全身模特照，见 `docs/spike/inputs.jpg`。

同一个请求：模特图 + 衬衫 + 牛仔裤 + "穿上这两件、衬衫塞进裤腰、换成周末咖啡馆窗边、小红书生活随手拍"。

| qwen-image-3.0-pro（多图编辑） | 两次都没拿到结果：只有同步接口，超过约 60 秒连接被切断 | > 60 秒 | 不适合交互式场景；只用来生成测试素材 |

### 2.3 文本与看图

| 用途 | 模型 | 理由 |
|---|---|---|

### 2.4 真实感复评：豆包 Seedream 5.0 pro（火山方舟）

真机走查后对成片真实感不满意（皮肤偏"塑料"、光线平），把百炼之外的候选拿进来同题对比。拿线上一张真实镜头的全部输入（同一套提示词、同一张模特照与两件衣服）各出一张：

| 方案 | 结果 | 耗时 | 价格（官方，北京） |
|---|---|---|---|
| wan2.7-image-pro（第一阶段默认） | 衣服还原准确；皮肤与光线偏平，人像略有"合成感"；吊牌已按规则去除 | 14 秒 | 0.50 元/张 |
| **doubao-seedream-5-0-pro-260628** | 同样的衣服还原，皮肤质感、自然光与姿态明显更像真人抓拍，背景景深与窗光层次更好；吊牌同样去除；最多 10 张参考图 | 42 秒 | 2K 档 0.60 元/张 + 参考图 0.02 元/张（首张免费） |

并排对比见 `docs/model-compare/wan27-vs-seedream50-shot1.jpg`（左 wan2.7，中 Seedream 5.0 pro，右为三张输入）。

结论：出图默认切到 Seedream 5.0 pro，wan2.7 保留为可在管理端一键切回的备选；视频、看图、对话不变。接入方式是同一个 `image()` 入口按模型名分流到方舟 `images/generations`（固定 1536×2048、不加平台水印，标识仍由服务端统一盖），对工作流零改动。Seedream 5.0 pro 是字节 2026 年中发布的旗舰出图模型，国内第一梯队；横向看与 GPT-Image 2、Nano Banana Pro 同档，文字渲染略逊、价格约为前者四分之一。它不支持组图和流式，这两项我们不用。

### 2.5 成本估算（单篇笔记）

按 6 张图 + 2 次改图 + 1 条 5 秒视频 + 对话和看图估算，单篇约 **9–10 元**（出图按最终默认的 Seedream 计；换回 wan2.7 约便宜 1 元）：

| 项 | 单价（官方，北京） | 用量 | 小计 |
|---|---|---|---|
| 豆包 Seedream 5.0 pro 出图/改图（默认） | 0.60 元/张 + 参考图 0.02 元/张 | 8 张 | 约 5.0 元 |
| wan2.7-image-pro（备选） | 0.50 元/张 | 8 张 | 4.0 元 |
| 图生视频 | 未查到 wan2.6-i2v-flash 单价，按 happyhorse 720P 约 0.9 元/秒作上限 | 5 秒 | ≤ 4.5 元 |
| qwen3-vl-plus 看图 | 输入 1 元 / 输出 10 元（每百万 token） | 约 2 万 token | < 0.1 元 |
| DeepSeek 对话 | 每百万 token 几元 | 约 10 万 token | < 0.5 元 |

对比传统商拍单套 200 元以上、周期按天计，成本和周期都低一到两个数量级。整个作业的模型花费约 110 元（含同题换模型对比与灵感墙素材）。

## 3. 智能体框架选型

### 3.1 先把场景翻译成框架必须满足的硬需求

| # | 硬需求 | 来自场景的哪里 | 做不到会怎样 |
|---|---|---|---|
| H1 | **会话状态持久化**：一个合作项目可能聊几天，服务重启、App 断网后从原处继续 | 博主不会一次聊完；服务要能发版 | 重启一次，脚本和已选方向全丢 |
| H2 | **人在回路**：花钱的步骤（出图、出视频）前必须停下等博主确认，确认后从停下的地方恢复 | 生成按张/按秒计费；品牌审脚本 | 智能体自作主张出 20 张图，钱花了方向还是错的 |
| H3 | **流程可控 + 局部自主**：大阶段有固定顺序（方向 → 脚本 → 出图 → 笔记 → 视频），阶段内自由对话和调用工具 | 品牌合作有交付顺序 | 纯自主智能体会跳步、漏步，没法对品牌交代 |
| H4 | **长任务不阻塞对话**：出图 15–45 秒/张、视频约 1 分钟，交给后台任务，完成后回到对话 | 批量出图 + 视频 | 对话卡死；App 一断线任务就丢 |
| H5 | **版本与回退**：改脚本、改图要留历史，能回到上一版 | 品牌反复改稿 | 改坏了回不去 |
| H6 | **模型无关**：文本用 DeepSeek、看图用通义、生成用万相，随时换 | 成本和效果都要能调 | 被一家模型绑定 |
| H7 | **能融进现有后端**：Python 服务里当库用，状态进自己的 Postgres，可观测 | 要部署到自己的服务器，代码给人审 | 只能在某个平台里跑，没法接业务表 |

### 3.2 候选框架对照（版本为 2026-10-20 PyPI 最新）

| 框架 | H1 持久化 | H2 人在回路 | H3 流程可控 | H4 长任务 | H5 版本回退 | H6/H7 | 结论 |
|---|---|---|---|---|---|---|---|
| **LangGraph 1.2.16** | Checkpointer 官方 Postgres 实现，按 thread 持久化 | `interrupt()` 任意节点暂停，`Command(resume=…)` 恢复 | 显式状态图：节点 + 条件边，阶段内可嵌工具调用智能体 | 节点内入队后 `interrupt` 等结果，Worker 完成后 resume | checkpoint 历史可查、可从任一历史点分叉 | 模型无关；纯库，状态在自己的库里 | **选用** |
| OpenAI Agents SDK 0.24 | Sessions 存对话历史；运行状态 `RunState` 可序列化 | 工具 `needs_approval`，审批后 resume | 以 handoff 和工具为主，没有显式阶段图 | 需自己编排 | 无内建 | 支持兼容接口的其他模型，但默认能力围绕 OpenAI 设计 | 审批模型只覆盖"工具级"，阶段流程要自己写 |
| Google ADK 2.12 | Session 服务可接数据库；App 级 resumability | 工具确认；2.12 起工作流节点 `require_confirmation` | 有 Workflow 智能体 | `LongRunningFunctionTool` | 无内建 | 在 GCP / Gemini 生态里最顺 | 能力在追，但国内模型和部署不是它的主场 |
| CrewAI 1.15 | Flow `@persist`（默认 SQLite） | `@human_feedback`（≥1.8） | Flow 有步骤；Crew 偏角色协作 | 需自己编排 | 无内建 | 多角色提示词开销大 | 适合快速做"多角色协作"原型，不是本场景的形状 |
| Microsoft Agent Framework 1.22 | 工作流带 checkpoint | 请求/响应式人工介入 | 有工作流图 | 支持 | 依赖 checkpoint | .NET / Azure 生态优先 | 可行，但国内落地和社区资料少 |
| AgentScope 2.0（阿里通义） | 2.x 有状态存储（Java 版支持 MySQL/Redis） | 2.x 支持暂停后原位恢复 | 以 ReAct 智能体和多智能体消息为主 | 需自己编排 | 无内建 | 国产模型适配好 | 适合多智能体对话/仿真；阶段化业务流程不是强项 |
| Dify / Coze | 平台托管 | 有限（表单节点） | 可视化工作流 | 平台内异步 | 平台版本 | 状态在平台里，难接自己的业务表；代码不可审 | 做演示快，但作业要求交付完整代码和可部署服务，不合适 |
| 不用框架（手写循环） | 自己存 | 自己写 | 自己写状态机 | 自己写 | 自己写 | 完全可控 | 24 小时内要把 H1–H5 写对、写稳，风险最高 |

（各框架能力以官方文档为准，以上是 2026-10 调研时的公开资料，详见文末来源。）

### 3.3 用小实验证明，而不是只列表格

服务端代码里每条硬需求都有对应的自动化测试或演示脚本：

- **H1**：选完方向后重启 api 容器，再发消息，智能体从原阶段继续，历史和卡片都在。
- **H2**：脚本未确认时调用出图工具被拒绝；确认动作通过 `Command(resume=…)` 恢复图执行。
- **H4**：出图任务入队后对话立即返回；Worker 完成后状态更新，App 轮询看到结果。
- **H5**：改图生成 version 2，`parent_id` 指向原图；脚本修改前后在 checkpoint 历史里都能查到。

实测结果（Mock 模式，`server/scripts/experiments.py`，2026-10-20 23:20）：

| 实验 | 对应需求 | 结果 | 用时 | 证据 |
|---|---|---|---:|---|
| E1 重启续聊 | H1 | PASS | 2.86 秒 | 选完方向后重启 API 容器，4 条消息、脚本和待确认点都在，继续对话正常 |
| E2 重复确认 | H2 | PASS | 2.24 秒 | 确认脚本发两次、同一指令改图两次，任务表仍是 4 张原图 + 1 次改图，没有重复花钱 |
| E3 越阶段 | H2/H3 | PASS | 0.02 秒 | 脚本阶段请求生成视频，被代码门禁拒绝，没有创建任务 |
| E4 时间旅行 | H5 | PASS | 0.12 秒 | 改成通勤风（v2）后用 `get_state_history` 恢复到 v1 并确认，已生成的图保留 |

阶段内 ReAct 的选工具准确率（真实 DeepSeek）：Codex 自建 30 句问句集 30/30；Claude 另写 16 句私有问句抽查（含"第二张背景有点乱""别聊了直接帮我出图""整体风格不对重来"这类模糊、越阶段、跑题的说法），全部选对工具，越阶段的请求由代码拒绝并用中文解释原因。

真实模型全链路（看图 → 3 个方向和预览图 → 脚本 → 改成通勤风 → 5 张图并打还原分 → 改图 → 笔记 → 5 秒视频）：5 张正式图还原分 93–96；单篇花费约 6 元（官方单价估算）。

### 3.4 反方意见和应对

**最强的对手是"不用框架"。** 一个 `while` 循环 + 一张存项目状态的 JSONB 表 + 一张事件表，大约 200 行就能跑通这 7 个阶段，更短、更透明。LangGraph 的重放语义反而带来了额外复杂度：任务 id 要做成确定性的（uuid5 去重键），恢复时要补齐业务表和 checkpoint 之间的差异。

我们的第一版确实踩中了这个反方意见：图只有"理解需求 → 等待 → 执行工具 → 等待"几个节点，阶段内靠关键词判断用户意图，回复是模板句——LangGraph 在里面只是"存在 checkpoint 表里的待确认字段"。外部评审指出后，第二版让框架挣到它的位置：

1. **阶段内 ReAct**：模型从当前阶段允许的工具里自己选、自己解析参数（"第二张"是哪张图），代码只管放行和花钱门禁。
2. **时间旅行**：脚本历史直接来自 `get_state_history`，博主可以回到任意一版——手写循环要自己做快照和版本表。
3. **流式中间结果**：看图卡片在节点内就推给 App，不用等整轮结束。
4. **interrupt 的重放安全**：确认动作重复发送、服务中途重启，都不会重复入队花钱（实验 E1、E2）。

**诚实的结论**：如果流程永远只有这 7 个阶段、只有一个博主，手写也够用；选 LangGraph 是为了公司链路往下长——多个智能体协作（选款、文案、审核分开）、更多人工确认点、跨天的长会话、需要回放和审计——这些都是图 + checkpoint 的原生能力。

**第二名是 AgentScope**：阿里开源、和百炼模型配合最好、实时打断做得好。如果团队全在阿里云和百炼上、更看重多智能体对话，它值得选；它的短板是阶段化业务流程和 Postgres 持久化不是一等公民。

## 5. 演进方向

按"离公司线上链路有多近"排序：

1. **多智能体分工**：把选款/审美、文案、合规审核拆成子图，主图负责编排；审核子图在发布前检查品牌禁忌词、AI 声明、敏感品类。
2. **还原度从"打分 + 重修"升级到"专用试衣 + 精修"**：高要求品类先走专用试衣模型（如 aitryon-plus）保证版型，再用通用生成模型换场景；还原分作为质检门禁和数据回流（低分样本进标注池）。
3. **博主风格记忆**：把博主历史笔记的风格、常用场景、口头禅存成长期记忆，方向建议和文案更像本人。
4. **资产中心对接**：衣服图、生成图、版本链进入资产中心，带自动打标和检索，和 MuseGate 现有资产体系打通。
5. **充值与结算**：点数账本已经按项目和用户汇总（10 点 = 1 元），接支付即可做"先充值后消耗、失败退点"和品牌方代付。
6. **真流式**：在工具调用参数流上做增量 JSON 解析，回复逐字出现。
7. **部署**：单机 docker compose → 业务后端（Java/Spring）+ AI 服务（Python）分开部署；Worker 按 GPU/外部 API 配额水平扩展；媒体进 OSS + CDN。
